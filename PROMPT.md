## Задание №1 — исправить возврат из паузы и восстановление после ошибки

Дата подготовки: 31.10.2026.
Приоритет: высокий.
Задание основано на чтении исходников ветки main. Описанные ниже причины найдены статическим анализом; запуск и воспроизведение в браузере ещё нужно выполнить.

### 1. Возврат из «Настроек» и «Управления» во время паузы

Основной файл: `src/stages/GameStage.ts`.
Связанные файлы: `src/ui/Screens.ts`, `src/core/InputManager.ts`.

Что видно в текущем коде:
- `pause()` допускает вход только при `state === 'playing'`.
- Затем `enterUI()` меняет состояние на `'ui'`, выключает ввод и освобождает мышь.
- Кнопки «Настройки» и «Управление» закрывают меню паузы, а обратным вызовом передают `() => this.pause()`.
- При закрытии вложенного окна состояние остаётся `'ui'`, поэтому повторный вызов `pause()` сразу возвращается.
- В результате меню паузы не восстанавливается, а игровой ввод остаётся выключенным.

Нужно:
- Отделить вход в паузу от повторного показа её меню либо сделать столь же небольшое и понятное исправление.
- После закрытия настроек/управления, открытых из паузы, снова показывать меню паузы.
- Мир не должен возобновляться до нажатия «Продолжить».
- «Продолжить» должно вернуть управление без нажатых «залипших» клавиш.
- Не открывать меню паузы поверх инвентаря, крафта, диалога, смерти или победы.
- Не допускать повторных окон или рекурсии от pointerlockchange.
- При отказе браузера в автоматическом Pointer Lock оставлять понятный путь захватить мышь кликом. Не считать программный вызов requestPointerLock гарантированно успешным.

### 2. Возврат в игру после перехваченной ошибки

Основной файл: `src/core/Game.ts`.

Что видно в текущем коде:
- В `loop()` при исключении устанавливается `this.crashed = true`.
- После этого условие `this.stage && !this.crashed` блокирует и update, и render.
- Кнопка «В меню» в `fatal()` вызывает `toMenu(true)`, но флаг `crashed` нигде не сбрасывается.
- Поэтому после такого возврата рендер и логика новой сцены могут остаться остановленными.

Нужно:
- Корректно сбрасывать состояние аварии при успешном восстановлении/установке рабочей сцены.
- Не сбрасывать флаг безусловно в каждом кадре: это скроет настоящую ошибку и запустит бесконечный поток исключений.
- Не обходить неудачную установку сцены как успешную. Проверь обработку ошибки в transitionTo и её then-обработчики.
- После успешного возврата в меню оно должно снова рендериться, и новая игра должна запускаться без перезагрузки страницы.
- Повторная ошибка должна снова показывать одно понятное окно, без накопления обработчиков/модальных окон.
- Не удалять сохранение ради восстановления.

### Проверка результата

Сначала добейся воспроизведения дефекта на исходном коде или зафиксируй, почему он уже исправлен.
Добавь небольшие регрессионные тесты поведения возврата из вложенных окон и восстановления после ошибки.
Для тестов допускаются заглушки renderer, screen callbacks и input; не требуется запускать целый WebGL-мир в каждом unit-тесте.
Тест должен проверять переход состояния и результат для игрока, а не просто наличие строки/метода в исходнике.

Выполни:
```text
npm run typecheck
npm test
npm run build
```

Проверь вручную в браузере:
1. Новая игра → Esc → Настройки → закрыть → снова видно меню паузы → Продолжить → управление работает.
2. Новая игра → Esc → Управление → закрыть → снова меню паузы → Продолжить.
3. Повторить оба сценария несколько раз; не должно быть дублирующихся окон и движения мира на паузе.
4. Проверить инвентарь/крафт/стройку и потерю фокуса окна: они не должны неожиданно открывать вторую паузу.
5. Один раз контролируемо вызвать исключение в update/render в тестовой среде → «В меню» → новая игра: кадры и управление восстановились. Тестовую инъекцию ошибки не оставлять в рабочем коде.
6. Повторное исключение после восстановления обрабатывается нормально; существующий прогресс не удалён.

Если браузер недоступен, честно напиши «браузерные сценарии не проверены», перечисли конкретные шаги для Алексея. Не называй сборку и unit-тесты визуальной проверкой.
